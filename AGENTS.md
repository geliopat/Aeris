# Aeris — обязательные инструкции разработчикам и ИИ-агентам

## 1. Источник требований

Перед началом задачи читать SPECIFICATION, ARCHITECTURE, ROADMAP, CONFIGURATION, PROVIDER-HEADERS, UI-SPECIFICATION, TESTING, COMPATIBILITY. Позднее явно утверждённое решение пользователя отменяет противоречащее раннее. Не расширять scope ради количества функций. Если контракт не утверждён, помечать TBD, не выдавать предположение за решение. Согласовывать существенные изменения. Не считать этот комплект существующим кодом или проверенными результатами.

## 2. Не нарушать

- Aeris — отдельный проект; не менять FlClashZ, его службы, файлы, ветки или automations.
- Windows 11 x64 / Windows 10 22H2 x64. Core Rust, GUI C#/WinUI3. Не подменять ядро внешним Mihomo/Xray/winws/winws2. Не добавлять Zapret1, самописную криптографию или C DPI FFI.
- Эталон Mihomo — сборка FlClashX. XHTTP/XUDP/REALITY/Vision — оригинальный Xray. Для DPI действует приоритет Flowseal на Zapret2, оригинального Zapret2 и zapret2-gui. Для WireGuard/AmneziaWG действуют официальные эталоны из UPSTREAM. Исследовать новые источники только на этапах 10 и 6 соответственно. Соблюдать лицензии, фиксировать ссылки и commits. Не копировать чужой код без проверки права использования.
- VPN/DPI независимы, DNS имеет собственный lifecycle. Не модифицировать прокси-транспорт DPI по умолчанию. Не допускать скрытых утечек или обхода Kill Switch. Не выполнять произвольные BAT/CMD/Lua OS commands от SYSTEM.
- CLI `aeris` из любой директории pwsh, GUI `Aeris.exe`, ядро `aeris-core.exe`, сервис `AerisCore`. Не полагаться на регистр файлов Windows. Не создавать alias clash.
- YAML подписки неизменяем, пользовательские правила отдельно и приоритетнее. Не вводить общий override, `nooverride`, Lua config overrides. Отдельный адаптированный Mihomo template Remnawave.
- Только два режима UI: без providermode простой, с providermode полный. Нет ручного переключателя, редактирования виджетов, IP в простом; полный IP всегда при наличии, без анонса. Соблюдать согласованное размещение UI и общий hover glow. Не возвращать старые макеты, popup выбора или ранее отвергнутые функции.
- Release/Nightly, без Preview. Нет отдельного полного backup/export настроек. Внутренний rollback остаётся. Не публиковать стабильный Release до gate 1.0.0.
- Не вводить телеметрию, аккаунты, лишние зависимости, неподтверждённые параметры и скрытые fallback. Не логировать токены/приватные ключи/полные URL подписок без защиты.

- Сохранять слабую связанность GUI/ядра/служб и версионируемые внутренние контракты. Полноценная система модулей, Plugin Manager, публичный API/SDK и каталоги отложены до стабилизации. Конкретные модули требуют разрешения владельца. Не загружать произвольный сторонний код в привилегированные процессы.

## 3. Рабочий процесс

1. Проверить актуальную ветку, файлы, требования и upstream refs. Не путать эталон с целевым репозиторием.
2. Сделать минимальный согласованный план, определить затронутые модули и тесты.
3. Изменить код, тесты, схемы/контракты и документацию совместно. Не оставлять дублирующий код и необъяснённый unsafe.
4. Запустить доступные проверки, сообщить команды, результаты, ошибки и недоступные среды. Не выдавать сборку за тестирование. Не отмечать непроведённый тест как PASS.
5. Проверить security, regressions, error paths, IPC compatibility, rollback и производительность по необходимости.
6. Подготовить проверяемый diff/PR, provenance, ограничения. Не сливать при fail обязательных тестах.
7. Создавать/изменять репозитории, запускать сборку, публиковать Release и менять инфраструктуру только в рамках полученного разрешения. Не запускать сборки в ответ на обсуждение дизайна или подтверждение пункта ТЗ.

## 4. Качество и безопасность

Rustfmt/Clippy/Cargo Test/Audit/Deny, Roslyn/dotnet format, unit/integration/fuzz. Асинхронность, bounded queues, cancellation, typed errors. Минимальные права, IPC ACL, явные capabilities, подписанные манифесты с доверенными ключами, хэши, atomic replace, path validation, архивы без traversal. Никаких случайных privileged shell scripts. Lua sandbox/изоляция по threat model, проверка лицензий/подписей ресурсов. Секреты DPAPI/redaction; нет автоматической отправки логов.

## 5. Отчётность

Отдельно указывать: что реализовано, что проверено, что не проверено и почему, что осталось, какие предположения сделаны. Утверждения о производительности и совместимости — только на основе реальных измерений/версий. Никаких обещаний фоновой работы без созданного механизма автоматизации. В каждом релизе обновлять документацию RU/EN, changelog, матрицу совместимости и manifest.

All referenced design documents are canonical in [Aeris-Core/docs](https://github.com/geliopat/Aeris-Core/tree/main/docs); do not maintain divergent copies.

## 6. Оркестрация в Codex

Запускай главную сессию из корня доверенной рабочей копии `geliopat/Aeris`. Проектная конфигурация в `.codex/config.toml` задаёт оркестратору `gpt-6.2-sol` с `high` и скорость Standard. Codex автоматически обнаруживает роли из `.codex/agents/`. Допускаются до трёх одновременно открытых дочерних потоков сверх главной сессии. Делегированием и интеграцией управляет главная сессия.

### Границы компонентов

| Роль | Область |
|---|---|
| `architect` | Архитектура, границы репозиториев, контракты YAML, API/IPC и зависимость этапов. |
| `core` | `Aeris-Core/crates/`, логика Rust, конфигурация, транспорт, маршрутизация, VPN/DNS/DPI и серверная логика API/IPC. |
| `frontend` | `Aeris/src/Aeris/`, WinUI 3, подписки, клиентские заголовки и клиентская сторона IPC. |
| `system` | Интеграция Windows, CLI/PATH, служба `AerisCore`, драйверы, WFP/TUN, операции установки и удаления. |
| `security` | Независимая проверка границ доверия, утечек, привилегий, секретов и поставки. |
| `qa` | Независимые проверки, регрессии, межоперационные тесты и доказательства совместимости. |
| `devops` | GitHub Actions, упаковка, Nightly, Release и отчёты об upstream. |
| `docs` | Канонические документы, матрица совместимости и состояние этапов. |
| `reviewer` | Независимое итоговое ревью интеграционного diff. |

Клиент находится в `geliopat/Aeris`, ядро в `geliopat/Aeris-Core`, а каталоги данных и стратегии в `geliopat/Aeris-Resources`. При работе вне Aeris укажи агенту доступную рабочую копию и базовый SHA нужного репозитория. Назначай владельца файлов ресурсов по задаче, учитывая контракт их потребителя в ядре.

Перед назначением работы сверяй канонические документы в `Aeris-Core/docs` и поручай агенту прочитать разделы, относящиеся к его компоненту. Привязывай каждую задачу и её проверку к ID из `REQUIREMENTS.md`, применяй `DECISIONS.md` при конфликте с ранними обсуждениями и бери утверждённые значения из `DEFAULTS.md`. Передавай ссылки на `AGENT-RESPONSIBILITIES.md`, `ROADMAP.md` и `STATUS.md` вместе с актуальными SHA, PR и результатами CI. Поздние решения владельца имеют приоритет. Открытый контракт оставляй TBD до его проработки и не пересогласовывай утверждённые требования.

Для конфигурации и подписок эталон — поддерживаемое подмножество Mihomo YAML из сборки FlClashX с расширениями Aeris и отдельным адаптированным шаблоном Remnawave. Приёмка требует межоперационных тестов существующих серверов и поддерживаемых протоколов. Побайтовая идентичность YAML FlClashX и FlClashZ вне критериев. Подтверждай заголовки, режимы клиента и шаблон раздельными проверками из `PROVIDER-HEADERS.md` и `COMPATIBILITY.md`.

Если задача требует записи в соседние репозитории, добавь только нужные рабочие каталоги к разрешённым каталогам главной сессии. Например, из корня Aeris с соседними рабочими копиями можно запустить `codex --add-dir ../Aeris-Core --add-dir ../Aeris-Resources`. Для чтения достаточно доступного каталога. Передавай роли по полю `name` из TOML, когда клиент Codex предоставляет выбор пользовательской роли.

### Делегирование и интеграция

1. Определи результаты, затронутые контракты, зависимости и достаточные проверки. Если несколько компонентов используют меняющийся контракт, зафиксируй его с владельцами до зависимых правок. Привлекай `architect` для сложных решений между компонентами. Для простой задачи используй главную сессию или подходящую недорогую роль. При ограничении квоты Plus запускай необходимые роли очередями, сокращай повторные прогоны и сообщай о недоступности модели до выбора замены.
2. Передай каждому агенту цель, репозиторий и базовый SHA, рабочий каталог, эксклюзивные пути записи или режим чтения, зависимости и ожидаемые проверки. Запускай независимые назначения параллельно. Для параллельных изменений используй отдельные Git worktrees, когда доступны и нужны. При общей рабочей копии разрешай запись в непересекающиеся пути. Изменения общих контрактов, файлов и lockfiles закрепляй за одним владельцем и интегрируй последовательно.
3. Собирай diff или SHA, результат проверок и известные пробелы. Проверь базу, область изменений и зависимости, затем интегрируй результаты по порядку. Возвращай ошибки владельцу файлов, проверяй его исправления и освобождай завершённые потоки для следующей очереди. Продолжай обычные этапы работы самостоятельно в рамках выданных разрешений.
4. Для изменений в коде и существенных изменений в контрактах или настройках поручай `qa` затронутые регрессии и `reviewer` независимое финальное ревью. При изменениях границ доверия привлекай `security` для отдельной проверки. Для небольших правок документации достаточно профильной проверки. Проверяющие работают отдельно от автора. Повторяй затронутые проверки после исправлений. Для изменений в подписках сохраняй подтверждённые сценарии FlClashX, FlClashZ и Remnawave в пределах `CONFIGURATION.md`, `PROVIDER-HEADERS.md` и `COMPATIBILITY.md`.
5. Сверяй GitHub Actions по точному SHA, conclusion и обязательным jobs. Применяй правила Nightly из `docs/RELEASES.md`. Стабильный релиз требует явного разрешения пользователя и полного gate 1.0.0 из `Aeris-Core/docs/TESTING.md`. Публикация релизов и обновление upstream-компонентов требуют разрешения пользователя. Используй отчёты upstream для оценки потенциальных изменений.
6. По завершении этапа обновляй канонический `Aeris-Core/docs/STATUS.md` с ревизиями, проверенными результатами, ограничениями и оставшейся работой. Обновляй профильную документацию при изменении контрактов и матрицу при появлении доказательств совместимости. Завершай задачу после применимых проверок. Если обязательная проверка недоступна, отмечай её как непроведённую с причиной и оставляй соответствующий этап открытым.
